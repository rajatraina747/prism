# Whole-Codebase Review — 23 September 2026 (v2.0.0)

Review of `main` at `996b33a`, covering the whole tree rather than the 2.0 diff.
Most of the effort went where a diff review can't look: pre-2.0 code, the four
engines sharing one queue, and whole-session behaviour. It sits beside
[REVIEW-2026-09-14.md](REVIEW-2026-09-14.md) and doesn't repeat it.
**CONFIRMED** means seen in the code, and where stated in live app data.
**SUSPECTED** means a repro is still needed. A `/code-review ultra` pass was
planned but never ran (the repo was too large for it), so this review is the
complete finding set. The fixes are scheduled into 2.0.1, 2.0.2 and 2.1 in
[ROADMAP.md](../ROADMAP.md#arcs-from-the-2026-09-23-review).

## P0: fix before the next release

- [x] **B-1 · High · The queue is never saved while anything downloads.**
  `AppProvider.tsx:163-166` debounces `saveQueue` by 300 ms, keyed on `queue`.
  Every progress event creates a new array (`queue-reducer.ts:76-87`, even for
  events it ignores), and yt-dlp emits every 250 ms (`download_manager.rs:400`),
  so the timer never fires. Nothing flushes on quit. *Scenario:* 3 concurrent
  downloads of a 50-video playlist, 40 finish, then ⌘Q. The 40 are already in
  history, but `queue.json` is the pre-batch snapshot, so on relaunch they
  download again as `name (1).mp4` and anything added meanwhile is gone. This is
  the same shape as the 1.8.1 archive P0. *Fix:* throttle with a 2 s `maxWait`
  and flush on exit. *An afternoon.* CONFIRMED (the repro is still to run).
- [x] **B-2 · High · Finished torrents never leave the librqbit session.**
  When the seeding policy is met, the loop only drops the item from `active`
  (`torrent.rs:733-744`), with no `session.delete` or pause. librqbit re-adds
  every persisted torrent at startup (9.0.1 `session.rs:861-893`). *Scenario:*
  under "Stop at 100%", a torrent keeps uploading after Completed and seeds on
  every launch, invisibly. With "Move completed to" on, librqbit is left
  pointing at the old folder and may re-download there (SUSPECTED). *Live
  data:* `3E250312…` finished on 21 Sep and is still in `session.json` with
  `is_paused: false`. *Fix:* `session.delete(id, false)` before the move, plus a
  test. *One-line.* CONFIRMED.
- [x] **B-3 · High · "Move to Trash" can target the whole download folder.**
  `resolve_completion_path` falls back to `output_dir` (`torrent.rs:1249`),
  which for a single-file torrent is the shared destination. Library sends
  `filePath ?? outputFolder` (`Library.tsx:213-216`), and `trashable_paths`
  accepts any directory under a root (`lib.rs:1170-1179`). *Live data:* row
  `4E48A5C7…` has `filePath` = `~/Downloads/Prism`, so trashing that row trashes
  every download. The Trash makes it recoverable, which is why it isn't
  Critical. *Fix:* return `None` rather than a shared folder, and refuse roots in
  Rust (S-3). *An afternoon.* CONFIRMED.
- [x] **B-4 · High · Two direct downloads with the same name corrupt each
  other.** No name is reserved per id. The second run reuses the path because
  the first's state file exists (`http_engine.rs:786`), fails the source check,
  and truncates the first run's `.prismpart` (`:359`). *Scenario:*
  `a.com/latest/download` and `b.com/latest/download` interleave into one file,
  and nothing catches it without a SHA-256. *Fix:* reserve names like yt-dlp's
  `reserved` map. *An afternoon.* CONFIRMED.

## Correctness

- [ ] **B-5 · Medium · A stop that arrives before an engine registers its id is
  a no-op.** Engines register only after awaiting: yt-dlp
  (`download_manager.rs:380`), torrents after up to 45 s of magnet metadata
  (`torrent.rs:555`), direct links after a probe of up to 75 s
  (`http_engine.rs:801`), conversions (`convert.rs:261`). The frontend invokes
  after two awaited `listen`s without re-checking `cancelled`
  (`tauri.ts:115-251`). *Scenario:* remove a magnet while it's fetching
  metadata. It then downloads with no owner, is persisted, and seeds on every
  launch. *Fix:* insert a pending entry with a cancel flag before the first
  await. *An afternoon.* CONFIRMED.
- [x] **B-6 · Medium · ffmpeg conversions survive quitting.** The Exit handler
  kills only yt-dlp (`lib.rs:2127-2130`), and a conversion's own process group
  outlives Prism. Whether it keeps encoding once its progress pipe breaks is
  SUSPECTED. *Fix:* a `convert::kill_all()` in the Exit handler. *One-line.*
- [ ] **B-7 · Medium · Windows: yt-dlp completions can lose their path.**
  `sanitizeFilename` (`utils.ts:30-38`) keeps `: ? * | " < >`. yt-dlp rewrites
  those on Windows, so `find_output_file` (`download_manager.rs:747`) misses the
  real file, and the item completes with no Play, Reveal, quarantine or move.
  *Fix:* `--print after_move:PRISM:PATH=%(filepath)s` instead of guessing.
  *An afternoon.* SUSPECTED (Windows-only).
- [ ] **B-8 · Low · Concurrent completions can wipe the content index.** It is
  read, modified and saved with no lock through one shared `.json.tmp`
  (`content_index.rs:120-150`), and the archive fires every call at once
  (`AppProvider.tsx:306-317`). A torn file parses as empty, so up to 5,000
  entries are lost. *Fix:* a static `Mutex` plus `spawn_blocking`. *Short.*
  CONFIRMED.
- [ ] **B-9 · Low · A 206's `Content-Range` start is never checked**
  (`http_engine.rs:486-501`), so a misbehaving server corrupts the file
  silently. *Short.* CONFIRMED.
- [x] **B-10 · Low · A `%` in the destination breaks yt-dlp's `-o`** (the folder
  part is never escaped, `lib.rs:535`, `tauri.ts:231`), so a `100% Music` folder
  fails every download. *One-line.* CONFIRMED.

## Security

- [ ] **S-1 · Medium · Watch folders get around the S-6 confirmation card.**
  Watch-folder links count as in-app intent (`tauri.ts:459-466`), and
  `.txt/.csv` files are scanned for links (`watch.rs:28,125`). *Scenario:* the
  user watches `~/Downloads` (the natural choice), and a web page
  auto-downloads `x.txt` holding a magnet or a URL. Prism then joins the swarm
  or runs yt-dlp with browser cookies, unconfirmed. Unrelated user files also
  get renamed to `.failed` (`:137`). *Fix:* send text-list links through the
  card, refuse a watch folder that is also the destination, and leave files that
  yield nothing unrenamed. *An afternoon.* CONFIRMED.
- [ ] **S-2 · Medium (defence in depth) · Prism's own commands aren't covered by
  the ACL.** `build.rs:12` has no app manifest, so all 60 commands
  (`move_to_trash`, `when_done`, `start_torrent`, `update_ytdlp`…) can be called
  from the player window. Its `core:default` also lets it emit `quick-add-url`
  or `watch-folder-links`, which main treats as in-app. The player's narrow
  capability therefore limits plugin commands only. *Fix:* an `AppManifest`
  command list with per-window allows, and no event emit for the player.
  *An afternoon.* CONFIRMED.
- [x] **S-3 · Medium · `move_to_trash` has no lower bound in Rust.** `~`,
  `~/Documents` and the destination all pass `validate_open_path`
  (`lib.rs:1178`), so together with S-2 the player window can trash home
  folders. *Fix:* refuse roots and their ancestors, or accept only
  Rust-recorded paths (Ideas #1). CONFIRMED.
- [ ] **S-4 · Low · `storage_summary` walks any folder it is given**
  (`lib.rs:1138`), unvalidated and on a runtime worker. *Fix:*
  `validate_open_path` plus `spawn_blocking`. CONFIRMED.
- [ ] **S-5 · Low · RSS polls silently bypass a SOCKS proxy** (`rss.rs:37`),
  revealing the user's IP and subscriptions on a schedule. *Fix:* reqwest's
  `socks` feature, or refuse like the direct engine does. CONFIRMED.
- [ ] **S-6 · Low · The 64 MB capture cap is checked per line**
  (`spawn.rs:126-145`, `lib.rs:184`), and `--dump-json` is a single line, so a
  hostile response is fully buffered first. *Fix:* bound line length in
  `forward`. CONFIRMED.
- [ ] **S-7 · Info · A torrent `.mkv` that is really an M3U/HLS playlist may make
  mpv fetch its entries.** *Fix:* consider
  `demuxer-lavf-o=protocol_whitelist=file` in `player_load`. SUSPECTED.

**Checked and holding:**
- Stream server: 32-byte OS-random token compared in constant time, exact Host
  match, no CORS, and CSP `default-src 'self'` blocks a webview `<video>`. The
  token does appear in `mpv.log`, for one launch.
- Player allowlist, plus `config=no load-scripts=no ytdl=no`.
- `--` before URLs, and `--ignore-config --no-plugin-dirs`.
- `clip.rs` rebuilds ranges from parsed values, and templates clean every path
  component.
- Explorer quoting, and deep-link origin (only Rust emits the external channels).
- Sidecars are hashed before extraction.

**The known-open `$APPDATA` item is closed.** Tauri 2.11.5 matches scopes with
`require_literal_separator: true` (`scope/fs.rs:238,523`), so `$APPDATA/*.json`
can't reach `torrent-session/`, `torrents/` or `engine/`. The files Rust reads
that the webview can write are `settings.json` (every consumer whitelists or
re-validates it), `content-index.json` and `player-state.json`, both benign. The
managed yt-dlp's `.sha256` sits beside the binary, so it detects corruption, not
tampering. That is fine while the webview can't reach that directory.

## Performance

- [ ] **P-1 · High · Every progress tick re-renders the whole app.** Context
  values are rebuilt on every render (`AppProvider.tsx:750-757`), callbacks that
  depend on `queue` (`:565-650`) break `QueueRow`'s `React.memo`, and Transfers
  isn't virtualized (`QueueTable.tsx:101`). That is O(N·Q) row renders per
  second, plus five O(Q) effect passes per tick. *Fix:* memoize the context
  values, read `queueRef` in callbacks, return the same array for ignored
  events, give progress its own store, and virtualize past ~100 rows. *An arc;
  the first three are an afternoon.* CONFIRMED.
- [ ] **P-2 · Medium · Blocking work runs on async workers:** the storage walk,
  index hashing, `which ffmpeg` on every start (`lib.rs:1835`), and
  `trash::delete_all`. *Fix:* `spawn_blocking`. CONFIRMED.
- [ ] **P-3 · Low · `import_torrent_file` sends bytes as a JSON number array**
  (`tauri.ts:486`), about 60 MB for a 16 MB torrent. *Fix:* raw IPC body.
  CONFIRMED.

**Verified as claimed:** 4/s emit throttle; 6 lookup, 16 yt-dlp and 16 direct
slots; 4 connections; Library virtualized; 2,000-row history cap
(`AppProvider.tsx:299`); a torrent's file list and pieces every 5 s. No lock is
held across mpv FFI: the worker has timeouts and a wedged flag, and a test
guards it.

## UX

- "Stop at 100%" doesn't stop uploading (B-2). Until B-2 ships, the setting's
  copy is untrue.
- The Trash dialog should name any *folder* it is about to trash.
- Completion reads the settings captured when the download started
  (`AppProvider.tsx:458-478`), so turning off notifications mid-download has no
  effect on that download.
- Watch folders rename files they don't own (S-1).

## Ideas (ranked)

1. **A completion ledger owned by Rust.** Open, trash, convert and index accept
   only paths an engine produced. This closes B-3/S-3 and most of what S-2
   exposes.
2. **One job registry across the four engines.** A pending entry at command
   entry and one `kill_all` fix B-5 and B-6.
3. **Queue persistence in Rust, or throttle plus flush on exit (B-1).** Losing
   queue state has now caused the most serious bug twice.
4. **`--print after_move:filepath` instead of guessing extensions** (B-7, split
   chapters).
5. **Progress kept apart from queue state**, and virtualized Transfers (P-1).
6. **An app-command ACL manifest** (S-2), with the capability test extended to
   cover commands.
