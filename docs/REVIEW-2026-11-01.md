# Prism review — 2026-11-01

Third-party review of branch `roadmap/2.4-p3` (11 commits past v2.3.2: PGP-verified
engine updates, A-1/A-2/A-4 refactors, React 19). Read from the code, not the docs:
the Rust command surface and path validation, the engine updater, stream server,
player, the HTTP, torrent and yt-dlp engines, the queue, and the frontend's intake,
queue, Library and detail-panel paths. The UI was rendered in the web demo (dark and
light, 1200×800 and the 900×600 minimum) with Playwright.

**Evidence:** vitest 49 files / 402 tests pass; `tsc --noEmit` clean; `npm audit`
shows six advisories, all in build tooling (Tailwind/PostCSS/glob), none in shipped
code; `cargo audit` (local DB) shows no vulnerabilities, only unmaintained transitive
crates under Tauri. `cargo test` was **not** run for this review.

**Overall:** the security posture is unusually strong for an app of this size, and
the earlier reviews' fixes hold up when read cold:

- Paths are canonicalized before checking. Download roots come only from the native
  folder picker. Network paths are refused before the filesystem is touched.
- The ledger gates every destructive or executing action.
- The player and its mpv options are tightly allowlisted.
- Engine updates are PGP-verified, with zip-slip and zip-bomb caps.
- The stream server is loopback-only with a token.
- Every external link waits for an explicit OK.

The real problems this time are **bugs where those hardening layers disagree with the
UI**: the UI shows buttons that the backend now refuses.

---

## 1. Bugs (fix first)

### B-1 (High) Torrents are recorded and quarantined only when *seeding* ends
- When a torrent finishes downloading, `torrent.rs:1085` resolves its path. The
  Library adds it at that moment (`queue.rs:584-588`, "Listed in the Library now, not
  when seeding ends").
- But `quarantine_torrent` and `record_finished` run only after the seeding loop
  breaks (`torrent.rs:1150`, `:1181`) or when the user stops seeding (`:1370`).

**Effects:**
1. **UX.** While a torrent seeds (hours, days, or forever), every action the ledger
   gates fails with *"Prism only does this with files it downloaded"*: Library
   *Play in Prism* (`Library.tsx:652`), Queue detail-panel *Play*/*Open*
   (`DetailPanel.tsx:513-523`), *Convert*, and *Move to Trash*. Seeding is the default
   (ratio 1.0), so this hits nearly every torrent.
2. **Security.** With *Seed forever*, a torrent's files **never** get
   `com.apple.quarantine` or Mark-of-the-Web. A torrent-delivered executable opened
   from Finder or Explorer skips Gatekeeper and SmartScreen, which is exactly what
   `quarantine.rs` exists to prevent.

**Fix:** quarantine and record on the first `stats.finished` edge, where
`finished_at` is set. Also record a multi-file torrent's own folder when it is added
(Prism owns that folder), so completed files inside it can be played while the rest
download. Add a regression test that a seeding torrent's path passes `require_recorded`.

### B-2 (High) Library "Play in Prism" always fails for multi-file torrents
- A multi-file torrent's `filePath` is its folder (`resolve_completion_path`).
- The Library offers *Play in Prism* for it. The comment at `Library.tsx:648` says
  mpv loads the folder "as a playlist".
- `player_load` calls `validate_open_path(path, allow_dir = false)` and
  `is_openable_media` (`player.rs:355-357`), so a folder is always refused with
  "File not found". The hardening made this button dead.

**Fix:** either hide the button when the entry is a folder and rely on the per-file
actions in the expanded list, or add `player_load_folder`. That command would build
the playlist in Rust from the recorded folder's media files, sorted, each passing
`is_openable_media`, and hand mpv files rather than the directory.

### B-3 (Medium) Queue detail panel builds wrong paths for multi-file torrents
- `DetailPanel.tsx:458,492` uses `${settings.destination}/${f.name}`.
- A torrent's file names are relative to its **own** folder. `holds_only` and
  `torrent_files` (`torrent.rs:2166-2199`) compare them that way. The real path is
  `destination/<name or name [hash8]>/<file>`.
- So Open, Play and Show in Folder on a completed file of a multi-file torrent point
  at nothing.
- The Library already does this correctly with `outputFolder` (`Library.tsx:63`).
  The queue item doesn't have `outputFolder` until the torrent finishes, because
  `torrent.rs:1106` emits it only after `finished_at`.

**Fix:** emit `output_folder` from the first tick (it's known once the torrent is
added) and use one shared `torrentFilePath(item, name)` helper in both places.

### B-4 (Low) React 19 logs an error on every page
"Encountered a script tag while rendering React component" comes from
`next-themes@0.4.6`'s inline anti-flash script. React 19 never runs it, and the CSP
(`default-src 'self'`, no inline scripts) would block it anyway, so it has never
worked in the app. Either drop `next-themes` (theming already goes through
`use-theme-sync`) or set the initial theme class from `main.tsx` before render. This
came in with the unreleased React 19 commit.

## 3. Performance

No hot-path problems found. The earlier P-items hold:
- Patches carry only what changed and keep object identity.
- Rows are memoized and virtualized.
- File lists and piece maps go out only when they change.
- Disk work runs on the blocking pool.

Small items:
- **P-1** `Library.tsx:188`: "Clear" on a status tab calls `removeFromHistory` once
  per row, which is O(n²) filtering over up to 2,000 rows. Add `removeManyFromHistory(ids)`.
- **P-2** `choose_destination`, `still_needed` and `saved_segments` call `std::fs`
  directly inside async commands. Each call is cheap, but on a NAS each `exists()` is
  a network round trip on an async worker. Move them into the existing
  `spawn_blocking` blocks.
- **P-3** Torrents don't check free disk space before adding. yt-dlp and direct
  downloads both refuse when space is short; a torrent fills the disk and fails partway
  through. Use `fs2::available_space` against the selected size in `start_torrent` and
  `parse_torrent`; it also gives the UI a figure for U-3.

## 4. UI / UX

The screens are consistent and calm. One accent colour, good empty states, and both
dark and light themes work. Observed at the 900×600 minimum window:

- **U-1** The 220px sidebar, with its ~180px-tall logo block, takes a quarter of the
  width. Queue rows then wrap the percentage onto its own line. Fixes:
  - a collapsible or icon-only sidebar under ~1000px;
  - a smaller logo block;
  - `whitespace-nowrap` on the stats line, dropping ETA before percentage.
- **U-2** The Dashboard keeps the pasted URL in the input after **Fetch** succeeds.
  Clear it once the item is queued.
- **U-3** The torrent file picker shows no free space. Show "Selected 48.2 GB · 31.0 GB
  free on this disk" and disable **Add** when it won't fit (depends on P-3).
- **U-4** Rows whose actions the ledger will refuse should be disabled with a reason,
  not fail with a toast. After B-1, B-2 and B-3 that should be rare.
- Already planned in Phase 4: Settings search, ⌘F, shortcut sheet, terminology pass,
  one destructive-action policy, empty-state actions, contrast and type scale.

## 5. Features (not already on the roadmap)

- **F-1** Sequential / "watch while downloading" mode per torrent. *Play now* streams
  one file, but `torrent.rs:15` says there is no sequential mode. librqbit's stream
  already prioritizes pieces, so a toggle that streams the selected files in order
  would cover box-sets.
- **F-2** Free-space forecast on the Dashboard: queued plus active remaining bytes
  against the free space on each destination (P-3 and `storage_summary` together).
- **F-3** Library: "Re-download" for **Missing** entries, using the same item
  settings, and "Locate…" to re-point a moved file. The second needs the picker to
  ledger-record the new path.
- **F-4** Subscriptions: a per-feed regex filter, plus a "dry run" that shows what the
  next check would take. Keywords exist; torrent-feed users expect regex.
- **F-5** Speed history: a small 24h/7d throughput chart in Statistics. The queue
  already samples progress every 250ms in Rust, so this is a ring buffer.
- **F-6** Copy magnet / Copy source link from the Library row's context menu.
- Already planned in Phase 5: page capture, Safari extension, LAN web UI, torrent
  creation, Smart mode.
